# MV Music Analyzer v0.8.7 — 適用前チェックの状態判定修正

## 原因
編集画面と改稿案JSON書き出しはrevision-proposal.jsの同じproposalを使用します。適用前チェックはgetProposal()から取得した深いコピーを保持します。コピー時にrevision_summary、reason、author_checks、確認メモは失われていませんでした。

問題はrevision-apply.jsの独立したapprovalsにありました。openProposal()でcarryChecks()により一度だけ状態を引き継ぐ一方、元コンテJSON読込時のreset()がapprovalsを空にし、inspect()は保存済みstatusではなくこの空のフラグを判定していました。警告もリセットで消えるため、元照合が取れても6項目が未確認になる症状でした。制作指示の記入もinspect()は参照せずcontent_confirmedだけを要求していました。

## 修正
confirmationState()が適用側のproposalから6項目のstatusを毎回直接読みます。consistentだけが有効です。未記載、unconfirmed、inconsistentは適用側の古いチェックフラグで上書きできません。6項目は適用画面で読み取り専用表示とし、変更は改稿案作成画面で行います。

adopt_proposalで6項目がconsistent、revision_summaryに制作指示があり、未確認事項が空で、再検討・未定・仮等の警告候補がない場合は、保存済み制作者記録に基づいて内容確定を評価します。語句だけで確定を推定するものではありません。警告候補や未確認事項がある場合は引き続き制作者の明示的な内容確認が必要です。既存の明示的な内容確認も保持しますが、6項目の未確認・不整合を回避することはできません。

元CUTと保存時の前後CUTが一致すれば、照合結果を判定に使用します。一致不能な接続情報には別の再確認理由を表示します。元CUT不一致、必要な解析参照の欠損、変更関連のエラー等の停止条件は維持します。既存指摘と今回の関連指摘の分類は変更していません。

元コンテの後読み込み後も、その時点の元コンテと同じ保存済みproposalから判定を再計算します。同一元コンテの再読込では手動の補足確認も不要に消しません。異なる元コンテ・解析を読み込む場合は適用側の補足確認と最終承認を解除しますが、proposalの内容・理由・status・メモは変更しません。編集画面で変更した後は、引き続き明示的な再引き渡しが必要です。

## 互換性と安全性
解析、コンテ、baseline、review、v0.8.4改稿案の構造は変更していません。baselineを再生成・変更しません。statusをconsistentに書き換える処理は追加していません。適用履歴の既存スキーマは維持し、判定に使用したproposal_author_checksとconfirmation_evidenceを追加して追跡可能にします。履歴のapplication_versionは0.8.7です。

適用可能は最終承認ではありません。最終承認後も元コンテのコピーに確認済み変更フィールドだけを反映し、mv_storyboard_revised_v0_8_7.jsonとmv_storyboard_revision_application_v0_8_7.jsonへ別ファイルで保存します。解析の+0.3秒は自動反映しません。

## 回帰テスト
A: 6項目consistent＋一致する元コンテ＋確定制作指示 → 適用可能。
B/C: 各6項目を個別にunconfirmed/inconsistentへ変更 → 適用不可。古いapprovals=trueでも回避不可。
D: 元CUT不一致 → 適用不可。
E: 元コンテの後読込・再読込 → 内容、理由、status、各メモを保持。
F: 「画面の改稿案を使用」→ 同じ確認状態で判定。
G: 最終承認前は生成・書き出し不可。承認後も他43 CUTと元データは不変。

既存v0.8.6コードを同じ合成入力で実行すると8件の未確認、修正後は0件となることを確認しました。実ユーザーの入力ファイルは存在しないため、テストは合成44 CUTです。実スマートフォンは未検証です。
